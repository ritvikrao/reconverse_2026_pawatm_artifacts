Adaptive queue polling: does re-apportioning the polling table help?
==============================================================================

Machine : NCSA Delta CPU node, 2x AMD EPYC 7763, 1 node, 1 process
Layers  : Reconverse (register-queues branch, with the adaptation added)
          vs the original Converse inside Charm++, which has a fixed
          scheduler and is the baseline.  Same benchmark sources build
          against both.
Runs    : all PEs in one process; progress polling left unregistered
          (+no_progress_polling) since a single process has no network
          traffic for it to progress.
Stat    : absolute columns are the median over repetitions.  The
          comparison columns are PAIRED -- the median of the per-
          repetition ratio -- because this node drifts between clock
          states and a whole repetition can be 40% slower than the next
          for every configuration alike.  The four configurations are
          launched back to back within a repetition, so the within-
          repetition ratio is drift-free.  (range) is min..max of those
          per-repetition ratios: where it straddles zero, the effect is
          smaller than the run-to-run noise and should not be read as a
          result.

How the adaptation works
------------------------------------------------------------------------------
The scheduler walks a 64-slot table; each slot holds a queue-polling
function, so the number of slots a queue holds is how often it is
polled.  Each PE counts the messages it pulls per queue.  Every 10 trips
around the table (640 scheduler iterations) those counters are
re-apportioned into slot counts by largest-remainder, and each queue's
slots are spread as evenly over the table as they fit.  Every registered
queue keeps at least one slot, so a queue that goes quiet can still be
found again when its traffic returns.

Registered frequencies at startup are nodeq=1, threadq=16, nodeprio=1,
threadprio=16 -- i.e. out of the box the per-PE thread queue is polled
16x more often than the shared node queue.

Queue mapping used by both benchmarks:
  shared / remote  CmiSyncNodeSendAndFree -> node queue, drained by every
                   PE on the node        (polled by pollConverseNodeQueue)
  local            CmiSyncSendAndFree(self) -> this PE's thread queue
                                        (polled by pollConverseThreadQueue)
A plain inter-PE send inside one process lands in the destination PE's
thread queue -- the same registered queue as a self-send -- so the table
would have nothing to distinguish.  The remote leg has to go through the
node queue to be a separate queue at all.

==============================================================================
Benchmark 1: parallel ring + local self-send streams
==============================================================================
Every PE injects one ring token into the shared queue (so the shared
queue is essentially never empty) and `streams` tokens into its own
local queue; each token is handled m times.  Sweeping `streams`
moves the traffic mix from all-shared to overwhelmingly-local.

==============================================================================
Benchmark 2: x shared-queue messages vs y local messages, drifting
==============================================================================
Each PE keeps x messages circulating through handler r (shared queue)
and y through handler l (its own local queue); each handler counts up
to m.  x and y are stepped slowly so the adaptation has time to
settle.  Total work per leg is ~p*m regardless of x and y -- x and y
set how many messages are in flight, i.e. the queue occupancy mix, so
what moves is the polling split rather than the amount of work.

==============================================================================
Reading these tables
==============================================================================
A comparison is only meaningful where its (range) excludes zero.  The
node's clock drift makes whole repetitions 30-40% faster or slower than
each other, which is far larger than any of the effects here, so a
median alone would be misleading.

From the 9-repetition run of 2026-07-30:

* Reconverse beats Converse at 32 of the 34 measured points, paired,
  with ranges that exclude zero -- by +15% to +70%.  The two remaining
  points (benchmark 1, 4 PEs, streams=64, and one 8-PE point) sit
  within the run-to-run noise.  Comparing the two non-adaptive
  configurations (Reconverse static vs Converse) isolates the layer
  itself; that is the 'stat v Conv' column.  This is the largest and
  most consistent effect in the data.

* Adaptation helps on benchmark 2 at both PE counts, and on benchmark 1
  at 4 PEs when the traffic is shared-queue-heavy.  The hitrate variant
  is the stronger of the two rules: +19..+30% over the static table on
  benchmark 2 at 4 PEs and +9..+17% at 8 PEs, with ranges that mostly
  exclude zero.  The literal count rule gains less and its ranges
  usually straddle zero.

* Adaptation HURTS on benchmark 1 at 8 PEs in the mixed regime
  (streams 2-8): -17% to -31% for count, -13% to -25% for hitrate, with
  ranges that exclude zero.  The slot tables show why -- from streams=2
  on, the table hands the per-PE thread queue 61 of 64 slots and leaves
  the shared node queue 1.  At 8 PEs the ring in that shared queue is
  the critical path, and starving it costs more than the extra local
  polling gains.  Allocating slots in proportion to message volume is
  the wrong objective when the low-volume queue is the latency-critical
  one.

* The allocation itself is stable and reproducible: every repetition of
  a given configuration settles on the same split, moving monotonically
  from nodeq=61/threadq=1 with no local streams, through 31/31, to
  nodeq=1/threadq=61 once local traffic dominates.  The mechanism does
  what it was asked to do; it is the objective that is wrong for the
  8-PE ring case.
