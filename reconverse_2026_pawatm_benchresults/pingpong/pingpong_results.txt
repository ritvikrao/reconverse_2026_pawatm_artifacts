Pingpong: one-way message latency
==============================================================================

Machine   : NCSA Delta CPU nodes, 2x AMD EPYC 7763, HPE Slingshot
Iterations: 1000 per message size
Sizes     : 16 to 262144 bytes, doubling
Statistic : median of 5 repetitions

Layout    : 2 processes, 1 PE each, in both sets.  The two sets differ
            only in whether those processes share a physical node.

Versions:
  old Converse             charm/benchmarks/converse/pingpong, built
                           -optimize -production -O3 against the
                           mpi-linux-x86_64-smp build
  Reconverse msg           tests/orig-converse/pingpong -- the same
                           benchmark on the ordinary send path
  Reconverse RDMA          tests/rdma_pingpong -- explicit one-sided
                           get on a registered CmiNcpyBuffer, with a
                           small message carrying the completion signal
  Reconverse persist+RDMA  tests/persistent_pingpong -- the message
                           benchmark with the timed sends routed
                           through a PersistentHandle, which registers
                           its receive buffers once at setup and moves
                           the payload with a one-sided put

Reconverse is built CMAKE_BUILD_TYPE=Release with autofetched LCI v2,
from `main` plus the new persistent pingpong only.  Both processes are
given 2 cores in every configuration, so the Converse comm thread does
not change the placement relative to Reconverse, which has no comm
thread.

LCI devices: the four compared versions all run +lci_ndevices 1, NOT
the 8 used for the task-bench runs.  Above one device the one-sided
get aborts inside LCI:

    backend_ofi_inline.hpp:post_get_impl:388
      <lci:Assert failed: false> err : Invalid argument

because the memory region is registered against one device while the
get is posted on another.  It reproduces at 2 devices and at 8, and
not at 1 or at the default, which is why reconverse's own CMake test
for rdma_pingpong passes no device flag.  Running two versions at 8
and two at 1 would make the columns incomparable, so all four use 1.
With one PE per process there is no concurrency for extra devices to
exploit in any case.

'Reconverse msg (8 dev)' is a supplementary fifth arm, not one of the
eight configurations: it is the message path at 8 devices, to show
what the device count is worth where it does work.

Notes
==============================================================================

Repetition spread is 2-16%, so the large ratios below are well clear
of the noise while anything inside roughly 0.85-1.15x is not.

1. The two placements give opposite answers at small messages, and
   that is the headline result.  Intra-node, old Converse is about
   2x faster than Reconverse's message path (2.0 vs 3.7 us at 64
   bytes): both are shared-memory copies, and Converse's is leaner.
   Inter-node, that reverses -- Reconverse is about 2.4x faster (3.5
   vs 8.6 us), because the Charm++ build goes through MPI while
   Reconverse goes to libfabric through LCI.  A single-number
   comparison of the two runtimes would hide this completely.

2. The message path has a latency cliff between 4 KB and 8 KB
   (7.4 -> 17.3 us inter-node, 7.2 -> 16.8 intra-node).  That is the
   eager-to-rendezvous switch, and it lands exactly at the
   LCI_ATTR_PACKET_SIZE=8192 carried over from the task-bench runs:
   messages larger than one packet stop being sent eagerly.  Neither
   the RDMA nor the persistent version shows the cliff, since both
   move the payload one-sided and never take the eager path.  The
   cliff is a property of that setting, not of the runtime -- raising
   LCI_ATTR_PACKET_SIZE would move it.

3. The persistent channel is the best large-message option and the
   only version that wins at 256 KB in both placements (3.34x
   intra-node, 1.28x inter-node vs old Converse).  It beats plain
   RDMA there because the receive buffers are registered once at
   setup rather than per transfer.

4. Below about 2 KB the persistent and RDMA versions are the slowest
   of the four.  Both pay a round trip for the completion signal on
   top of the transfer, which dominates when the payload is small;
   one-sided transport only pays off once the payload is large
   enough for that fixed cost to amortise.

5. The supplementary 8-device arm is within noise of the 1-device
   message path at every size, so pinning all four versions to 1
   device to accommodate the RDMA limitation costs nothing here.
