Pingpong: one-way message latency
==============================================================================

Machine   : NCSA Delta CPU nodes, 2x AMD EPYC 7763, HPE Slingshot
Iterations: 1000 per message size
Sizes     : 16 B to 64 MB, doubling (23 sizes)
Statistic : median of 5 repetitions

Layout    : 2 processes, 1 PE each, in both sets.  The two sets differ
            only in whether those processes share a physical node.

Versions:
  old Converse             charm/benchmarks/converse/pingpong, built
                           -optimize -production -O3 against the
                           mpi-linux-x86_64-smp build
  Reconverse msg           tests/orig-converse/pingpong -- the same
                           benchmark on the ordinary send path
  Reconverse RDMA          tests/rdma_pingpong -- explicit one-sided
                           get on a registered CmiNcpyBuffer, with a
                           small message carrying the completion signal
  Reconverse persist+RDMA  tests/persistent_pingpong -- the message
                           benchmark with the timed sends routed
                           through a PersistentHandle, which registers
                           its receive buffers once at setup and moves
                           the payload with a one-sided put

Reconverse is built CMAKE_BUILD_TYPE=Release with autofetched LCI v2,
from `main` plus the new persistent pingpong only.  Both processes are
given 2 cores in every configuration, so the Converse comm thread does
not change the placement relative to Reconverse, which has no comm
thread.

LCI devices: the four compared versions all run +lci_ndevices 1, NOT
the 8 used for the task-bench runs.  Above one device the one-sided
get aborts inside LCI:

    backend_ofi_inline.hpp:post_get_impl:388
      <lci:Assert failed: false> err : Invalid argument

because the memory region is registered against one device while the
get is posted on another.  It reproduces at 2 devices and at 8, and
not at 1 or at the default, which is why reconverse's own CMake test
for rdma_pingpong passes no device flag.  Running two versions at 8
and two at 1 would make the columns incomparable, so all four use 1.
With one PE per process there is no concurrency for extra devices to
exploit in any case.

LCI registration cache: DISABLED (LCI_ATTR_USE_REG_CACHE=0).  Reconverse
commit 6b3233f enables it by default for autofetched LCI, but on these
nodes LCI reports it as "not available (status=-22)" and it measures
identically on and off at every size and version -- while ON, the message
path SEGFAULTS in liblci-ucx.so at 32 MB and above.  Disabling it costs
no bandwidth, removes the crash, and matches the original runs, which
predate that commit and therefore had no cache either.

'Reconverse msg (8 dev)' is a supplementary fifth arm, not one of the
eight configurations: it is the message path at 8 devices, to show
what the device count is worth where it does work.

Notes
==============================================================================

Repetition spread (max-min)/min is 1-52% across the middle 90%
of points, so ratios well outside that band are real and ones inside
it are not.

1. Small messages (64 B), old Converse vs the Reconverse message
   path:
     intra-node    2.08 us vs   3.36 us -- Converse faster by 1.62x
     inter-node    8.30 us vs   3.10 us -- Reconverse faster by 2.68x

2. Message-path latency step, 1node: 4 KB -> 8 KB takes 4.6 us -> 15.6 us
   (3.42x).  This is the eager-to-rendezvous switch at
   LCI_ATTR_PACKET_SIZE=8192; the one-sided versions do not show it.

3. Peak effective bandwidth (GB/s) and the size it occurs at:
     2 processes on 1 physical node (intra-node)
       old Converse                 6.12 GB/s at 8 MB
       Reconverse msg              22.71 GB/s at 16 MB
       Reconverse RDMA             23.25 GB/s at 64 MB
       Reconverse persist+RDMA     22.50 GB/s at 8 MB
       Reconverse msg (8 dev)      22.58 GB/s at 16 MB
     2 processes on 2 physical nodes (inter-node)
       old Converse                18.05 GB/s at 16 MB
       Reconverse msg              23.60 GB/s at 16 MB
       Reconverse RDMA             24.02 GB/s at 32 MB
       Reconverse persist+RDMA     21.58 GB/s at 16 MB
       Reconverse msg (8 dev)      23.43 GB/s at 16 MB

4. Bandwidth that COLLAPSES above its peak rather than holding:
     1node   Reconverse msg             22.71 GB/s at 16 MB -> 7.39 at 64 MB (-67%)
     1node   Reconverse msg (8 dev)     22.58 GB/s at 16 MB -> 4.72 at 64 MB (-79%)
     2node   old Converse               18.05 GB/s at 16 MB -> 6.17 at 64 MB (-66%)
     2node   Reconverse msg             23.60 GB/s at 16 MB -> 6.54 at 64 MB (-72%)
     2node   Reconverse msg (8 dev)     23.43 GB/s at 16 MB -> 4.39 at 64 MB (-81%)
   Only the copy-based/two-sided paths do this; the one-sided RDMA and
   persistent versions hold their bandwidth to the top of the range.
   It affects old Converse as well as Reconverse, so it is a property
   of moving the payload through the CPU at these sizes, not of either
   runtime -- note the onset sits at this machine's 32 MB L3 per CCX.

5. The supplementary 8-device arm differs from the 1-device message
   path by a median of 3.3% (max 15.1%) at sizes up to 16 MB, so the
   device count buys nothing at one PE per process.  Above that both
   arms fall off the cliff in note 4 and are not comparable there.
